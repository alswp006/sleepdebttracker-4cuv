# Architecture Review
Generated: 2026-07-30T18:46:43.184Z
Score: 74/100

## Summary
The codebase is generally well-organized with a clear layered structure (lib → hooks → components → pages) and no circular dependencies detected. However, there is notable duplication of small utility logic (haptics, tab config, date helpers) across pages, a handful of unused/dead exports, and inconsistent patterns for async data loading, error handling, and import paths that should be cleaned up as the app grows.

## Issues
### Warnings
- [duplication] The identical TAB_ITEMS array (홈/리포트/플랜/설정 routes) is redefined in four separate page files instead of being defined once and reused. — Files: src/pages/Home.tsx, src/pages/PlanPage.tsx, src/pages/ReportPage.tsx, src/pages/SettingsPage.tsx / Fix: Extract TAB_ITEMS into a shared constant (e.g. src/lib/navigation.ts) or make it a default prop inside FloatingTabBar so it's defined once.
- [duplication] A near-identical safeHaptic/fireHaptic try/catch wrapper around generateHapticFeedback is reimplemented separately in BottomCTA.tsx, Home.tsx, RecordPage.tsx, SettingsPage.tsx, SleepTypePage.tsx, and inline in FloatingTabBar.tsx, each with slightly different type signatures. — Files: src/components/BottomCTA.tsx, src/pages/Home.tsx, src/pages/RecordPage.tsx, src/pages/SettingsPage.tsx, src/pages/SleepTypePage.tsx, src/components/FloatingTabBar.tsx / Fix: Extract a single triggerHaptic(type) helper into a shared module (e.g. src/lib/haptics.ts) and import it everywhere instead of redefining the try/catch.
- [dead_code] storage.ts exports getItem, setItem, and removeItem, but every consumer (records.ts, settingsStore.ts, streak.ts) uses safeGet/safeSet instead — the three functions appear unused anywhere in the codebase. — Files: src/lib/storage.ts / Fix: Remove getItem/setItem/removeItem if unused, or consolidate all call sites onto a single get/set API.
- [consistency] Data-loading pattern is inconsistent across hooks: useDashboard and useWeeklyReport wrap synchronous localStorage reads in useEffect + a loading flag, while useTodayRecord and useReward read the same kind of synchronous data directly via useState's lazy initializer with no loading state. — Files: src/hooks/useDashboard.ts, src/hooks/useWeeklyReport.ts, src/hooks/useTodayRecord.ts, src/hooks/useReward.ts / Fix: Standardize on one approach — since all reads are synchronous localStorage access, drop the artificial useEffect/loading pattern (or extract a shared useLocalStorageQuery hook if async-readiness is intentionally reserved for future API migration).
